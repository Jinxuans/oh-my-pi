# OMP 公司模式总方案

在 OMP 中建立可以跨会话、跨项目长期存在的 **AI 公司**。人类是董事会，OMP 主对话是 CEO 的交互入口，员工复用 OMP 子 agent 完成工作。借鉴 Paperclip 的组织、任务协作和治理机制，公司目标、人员、工作记录与权限由 OMP 公司服务持久管理。

这是拟建设的公司模式。[总体思想与架构](architecture.md)记录设计原则、数据归属和执行边界，[实施计划](implementation-plan.md)记录源码接入点和验收条件，[实施台账](implementation-tracker.csv)记录任务进展、阻塞及验收证据。

## 1. 一台电脑可以有多家公司

同一 OMP 环境可保存软件研发、内容创作、技术研究等多家公司。每家公司分别维护目标、部门、人员、报告关系、会话、项目、任务、文档、决策、审批、工具权限、预算和运行配置。用户可以进入或切换公司，空闲公司以持久数据存在，成员按需启动。

公司是长期组织，一个公司可以关联多个项目和工作目录。项目和目录决定工作在哪里开展，公司决定目标、成员和权限属于谁。首版每个 OMP profile 一次激活一家公司，切换前收尾或取消当前运行并确认停止写入。

## 2. 人类董事会与各岗位的职责

| 角色 | 职责 |
|---|---|
| 董事会 | 设定目标、任免或授权成员、管理预算和审批规则，查看工作、决定和运行情况。 |
| CEO | 通过主对话理解董事会意图，组织工作、协调各部门、处理升级事项、汇报决策和结果。 |
| 部门负责人 | 负责其业务范围内的计划、分工和跟进，例如 CTO 管理研发任务与技术人员。 |
| 员工 agent | 认领任务，与相关人员协作，提交工作成果和可复核的证据。 |

CEO 是长期岗位，董事会可以调整担任者。关闭主对话后，公司继续存在。再次进入时打开已绑定的 CEO 会话，或从当前目标、任务、审批和已批准决策重建上下文。成员可以直接协作，跨部门冲突、重大风险和超出授权的事项才升级。

## 3. 成员身份和 OMP agent 配置

- **OMP agent 定义**负责模型、工具、skills、角色指令和可派生 agent 等执行配置。
- **公司成员**负责长期身份、部门、职称、上级、项目范围、公司权限、预算和启停状态。可以复用同一个 agent 定义，并按公司规则选择模型或授权工具。
- 职称、汇报线和授权分别配置。一个成员即使担任 CTO，也只在获得授权的项目和资源上执行相应动作。会话、成员身份和每次运行分别记录。

## 4. 复用 OMP 子 agent 执行

公司服务管理持久任务、成员身份和调度，实际工作交给 OMP 现有子 agent 和会话能力。一个 OMP 进程可按需承载多个成员执行。空闲成员无需消耗模型请求，可暂停或释放会话，后续恢复或从持久状态重新开始。并发工作受模型请求、内存、工具执行和预算约束。

汇报关系记录在公司组织结构中。CEO 可以指派 CTO，CTO 可以通过工作项指派工程师，公司服务按需启动执行。OMP 原有的派生规则、递归深度和工具策略继续约束实际调用。

## 5. 围绕工作项协作和交付

典型流程是 **董事会提出目标 → CEO 组织工作 → 部门负责人拆分指派 → 员工执行并提交 → 相关成员审核 → 记录结果并汇报**。审核打回后，员工可在同一工作项继续提交，保留历次提交与审核意见。

工作项记录所属公司、项目和目标、负责人、状态、优先级、验收标准、父子关系和阻断依赖。评论、跨部门请求、审核意见和产物与任务一起保存。同一工作项同时只有一个有效执行者。不同任务写同一目录时单独处理工作区互斥或隔离，后续可利用 Git worktree 并行交付并协调合并。

## 6. 跨部门发现和通信

成员可以按职责查找应该联系的人，在任务中评论、提及成员、提出跨部门工作或评审请求。运行中的定向沟通在后续交付。重要结论回写工作项、文档或决策记录。消息、收件箱和搜索结果按公司与项目权限提供，唤醒由明确的派单或协作请求触发。

## 7. 长期记忆与上下文

长期保存目标与制度、组织结构、任务及依赖、文档及修订、附件和工作产品、评论与收件箱、审核、决策与理由、审批人和运行记录。正式决策有提议、批准、拒绝和被替代等状态。只有通过授权流程的决定才用于更新制度。

每次运行先加载与成员身份、权限和任务相关的当前状态，再按需查阅资料和历史。会话保留为可查阅记录。文档批注定位到相应版本，检索返回带权限和版本的引用。

## 8. 权限、审批、预算与运行边界

- **工作审核**决定成果通过或打回，结论绑定被审核的成果版本。
- **动作审批**授权具体动作，例如发布、删除数据或使用敏感资源。公司服务在动作入口校验公司身份、权限、目标、参数和版本，记录审批及执行结果。
- 公司预算和成员配额由公司服务归集和执行。并发预算按可计量请求预留与结算，未知用量单独显示。
- 应用层的授权覆盖受控工具。需要限制完整 shell 和宿主凭证时，另用进程、操作系统或沙箱隔离。
- 公司记录在 OMP 关闭后继续保存。默认调度随前台退出停止。定时唤醒或关闭界面后继续执行属于后续显式启用的能力。

## 换会话后从这里继续

1. 先读本页，确认长期目标、角色和产品边界。
2. 读[总体思想与架构](architecture.md)，确认公司服务、OMP 执行、持久状态和权限的职责边界。
3. 打开[实施计划](implementation-plan.md)，定位当前阶段的范围、源码接入点、验收和降级条件。首版验证本地研发团队的完整闭环，后续再扩到并行工作区、即时协作、资料管理与完整治理。
4. 在[实施台账](implementation-tracker.csv)查找当前阶段及前置条件已满足的任务，按编号接续，并把结果、证据和范围变更写回仓库。
